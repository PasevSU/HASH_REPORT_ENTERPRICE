# V92 — План на надграждането: вграден PDF в COMBO отчети и позиция

Изходно състояние: `V92_CURRENT_STATE_BG.md`. Този документ описва **какво се
добавя**, **защо точно така**, **кои опции не се побират в един панел** и **как се
проверява**.

## 1. Задача

Досега вграждането на PDF съществуваше само за отчет от един файл (`SINGLE_PDF`).
Отчетът за папка (`COMBO`) нямаше как да включи конкретен документ, а позицията на
внесените страници беше фиксирана.

Изисквания:

1. Вграждане и в COMBO отчети — „точно както при `single_pdf`, но на първите или на
   последните страници“.
2. Явна позиция: **преди** или **след** хеш отчета.
3. Новите типове да се виждат в името на файла и в архива, огледално на `SINGLE_PDF`.
4. Да не се променя досегашното състояние — само надграждане.
5. Опциите, които не се побират на един панел, да живеят в изскачащ диалог.

## 2. Решение

| Аспект | Решение |
|---|---|
| Имена на типовете | `COMBO_PDF` и `COMBO_ALL_PDF` |
| Профили | `combo_pdf` (текуща папка), `combo_all_pdf` (с подпапки) |
| Позиция | `before` / `after`, по подразбиране `after` |
| Име на изхода | `..._TYP_COMBO_PDF.pdf` и `..._TYP_COMBO_ALL_PDF.pdf` |
| Вход | `COMBO_PDF` включва **един избран** PDF; `SINGLE_PDF` включва **самия входен файл** |
| Съвместимост | Всички нови аргументи са допълнителни; старите извиквания работят непроменени |

`_ALL` се вмъква преди `_PDF`, защото генераторът винаги пише `_COMBO` и само
публикуването добавя суфиксите. Това дава `COMBO_ALL_PDF` и никога `COMBO_PDF_ALL` —
същият ред се спазва и в JS клонинга (`documentName()`), за да не се разминат двете
издания.

## 4. Анализ на опциите: какво остава на панела и какво отива в диалог

Панелът Run трябва да остане четим при 125% мащаб и на екран 1366×768. Затова е
направено разделение по **честота на използване**, а не по важност.

| Опция | Къде живее | Защо |
|---|---|---|
| Вграждане включено/изключено | Панел (отметка) | Основно решение на всяко пускане |
| Позиция преди/след | Панел (два радиобутона) + диалог | Едно кликване, но и обяснение в диалога |
| Път до PDF за вграждане | Панел (поле + `Choose PDF`) | Вижда се веднага кой файл ще влезе |
| ERLAEUTERUNG към отчета | **Диалог** | Използва се само когато файлът съществува |
| Включи подпапките | **Диалог** | Зависи от това дали целта е папка |
| Друга изходна папка | **Диалог** + собствен панел `Output` | Пътят е дълъг; полето не се събира на един ред |
| Тип на отчета | Автоматично от целта (диалог за обяснение) | Ръчният избор е източник на грешки |
| Филтри (`*eml.pdf`, каскадни) | Отделен панел Selection/Filters | Многоредов вход; не се побира в един ред |
| Изричен списък файлове | Отделен панел Selection/Filters | Изисква таблица и проверка |
| Архив / SQLite / TSA / инструменти | Страница Settings | Конфигурация, не операция |

Практични опции, които бяха преценени и **не** са добавени като отделни контроли:

| Кандидат | Решение | Причина |
|---|---|---|
| Вграждане на повече от един PDF | Отказано | Прикаченият файл е един по договор; няколко файла правят „оригиналът“ двусмислен |
| Вграждане във всяка страница/интерлийн | Отказано | Не съществува смислено правно приложение |
| Избор на диапазон страници от източника | Отказано | Внесените страници трябва да са целият оригинал, за да съвпада с хеша |
| Компресия/преоразмеряване на внесените страници | Отказано | Нарушава гаранцията за геометрия и байтова идентичност |
| Парола за шифрован източник | Отказано | Мълчаливото отваряне на защитен файл е правен риск; кодът е `..._SOURCE_ENCRYPTED` |
| „Позиция на всяка страница“ (mixed) | Отказано | Един отчет = една позиция; смесената подредба обърква проверяващия |
| Подписване на прикачения файл | Отказано | Файлът трябва да остане точно това, което е бил подписан |
| Отделна папка за прикачения файл | Отказано | Оригиналът пътува вътре в отчета; външно копие чупи байтовата идентичност |

## 5. Поведение при грешка (fail-closed)

| Ситуация | Резултат |
|---|---|
| Позиция извън `before`/`after` | `EMBED_POSITION_INVALID` преди всякаква работа |
| Има и `--embed-pdf`, и `--source-pdf` | Отказ: „either a single-file PDF or a chosen PDF, not both“ |
| Вграждане при `mode != combined` | Отказ |
| Избраният PDF не съществува | `EMBED_PDF_SOURCE_MISSING` |
| Избраният PDF е самата цел | „Cannot embed the evidence target inside the report“ |
| Профил `single`/`single_pdf` + избран PDF | Отказ: „only supports a combo report profile“ |
| Профил `single_pdf` без вграждане | Отказ: типът обещава вграден PDF |
| Шифрован източник | `..._SOURCE_ENCRYPTED` (проверка преди инспекцията на подписа) |
| Изходът би презаписал целта или прикачения файл | Отказ |

## 6. Съвместимост

* `Pipeline.run()` получава новите аргументи **след** съществуващите; GUI подава
  `_run_args` позиционно, затова само се **добавят** елементи в края.
* `--embed-position` по подразбиране е `after`, което е и старото поведение.
* `EMBED_CODES` в JS остава експорт за старите извиквания; новите кодове са в
  `embedCodes(kind)`.
* Нито един съществуващ тип не е преименуван; `SINGLE_PDF` работи както преди.

## 9. Рискове

| Риск | Мярка |
|---|---|
| Двете издания се разминат в името на изхода | Едно правило, проверено и в двата теста |
| Голям вграден PDF надува отчета | Одитът записва `attachment.bytes`; размерът се вижда в лога |
| Внесените страници чупят PDF/A-2b | Внасянето е **след** нормализацията; твърдението за PDF/A покрива само авторските страници |
| Шифрован PDF блокира конвейера със сурова грешка | Проверката за шифроване е преди инспекцията |
| Стар GUI подава по-къс `_run_args` | Новите аргументи са в края на кортежа |
